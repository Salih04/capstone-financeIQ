# R3-LEGACY-01 — Legacy database scoring and sector-path audit

**Audit date:** 2026-07-13
**Status:** evidence memo only; no application, schema, data, experiment, artifact, test, configuration, score, ranking, or model behavior changed. The binding packet permits this new memo and no other modification (`FINANCEIQ_AGENT_TASK_QUEUE.md:405-414`).

## Executive conclusion

FinanceIQ has three distinct live scoring families, and only one is the legacy database family. The trusted-CSV research score ranks available features without filling missing values (`backend/app/services/research/scoring.py:1-17`, `backend/app/services/research/scoring.py:68-108`), while the current CSV forecasting service excludes `sector` from features and produces within-year percentile rankings (`backend/app/services/forecasting_csv_service.py:44-49`, `backend/app/services/forecasting_csv_service.py:455-498`). Those paths must not be retired as part of legacy cleanup.

The database scoring family is nevertheless runtime-reachable: `app.main` imports all ORM models and registers both the unprefixed scoring router and forecasting router without a sector or legacy feature flag (`backend/app/main.py:10`, `backend/app/main.py:79-93`). Its routes call database scoring, adaptive-weight, sector-normalization, winner-cohort, and quarterly-fundamental services (`backend/app/routers/scoring.py:50-190`, `backend/app/routers/forecasting.py:54-267`). “Live” in this memo therefore means registered and callable in the application, not evidence of production traffic or valid inputs.

No repository evidence establishes a validated, point-in-time sector taxonomy for those computations. The trusted pipeline deliberately writes null sector identity, the sanctioned trusted database loader creates new companies without sector values, and all three committed modeling/universe CSVs audited here have zero nonblank sector rows (`scripts/data_collection/pipeline.py:136-146`, `backend/scripts/load_trusted_yearly.py:102-117`, `METHODOLOGY.md:52-82`). The legacy services group exact database strings and can calculate a sector percentile with two peers (`backend/app/services/sector_service.py:23-42`, `backend/app/services/sector_service.py:97-166`). Historical sector membership, point-in-time sector evidence, sector-neutral evaluation, and predictive validity are therefore **not established**.

The highest claim risks are: a 70/30 sector blend can be attached to a score from unprovenanced rows (`backend/app/services/scoring_service.py:789-848`); adaptive weights describe exact-string sector “performers” without a validated sector history (`backend/app/services/adaptive_weights_service.py:265-320`); the legacy heatmap replaces an all-missing cell with `0.0` (`backend/app/services/forecasting_service.py:1096-1114`); and the registered portfolio endpoint emits “increase” and “reduce” actions, contrary to the repository’s research-support/not-investment-advice boundary (`backend/app/services/forecasting_service.py:1117-1181`, `PRD.md:39-48`). These are audit findings, not implementation changes.

**Recommendation:** first demarcate the whole database family at runtime as “legacy — provenance unvalidated,” then require observed deployment/traffic evidence and a validated input-provenance decision before choosing quarantine or retirement. **Owner decision required.** The packet’s alternative owner options remain: visible demarcation, quarantine behind an environment flag, or retirement (`FINANCEIQ_AGENT_TASK_QUEUE.md:405-414`).

## Audit method and classification contract

The audit followed imports from `app.main`, router registration, route-to-service calls, service-to-ORM queries, model discovery through `app.models`, Alembic metadata and revision history, frontend API strings and page registration, scripts, tests, fixtures, configuration references, documents, and registered generated outputs (`backend/app/main.py:10-93`, `backend/app/models/__init__.py:1-39`, `backend/alembic/env.py:7-18`). Absence of a direct import was never treated as sufficient evidence of dead code.

Every row below has exactly one classification:

- **live production/runtime dependency** — imported/registered and callable in the normal application graph; this does not prove traffic, good data, or predictive validity.
- **test-only dependency** — preserved by a test or fixture, with no live caller established by this audit.
- **migration/history dependency** — required to describe or construct historical schema state.
- **compatibility dependency** — supports an optional/manual/legacy workflow or stored contract, but no normal frontend caller was established.
- **documentation-only reference** — prose or historical evidence with no executable role.
- **unreachable/dead candidate** — shadowed or no caller/consumer found after import, symbol, route, ORM, configuration, and frontend searches.
- **unresolved** — evidence is insufficient to assign a stronger reachability or ownership conclusion.
